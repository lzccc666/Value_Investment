# 008_分析师视角引擎

## 模块定位

008 是“分析师视角引擎”，用于让不同投资框架基于同一家公司当前已入库的数据快照，生成相互独立、可追溯、结构化的分析师视角。

本模块只做分析师视角分析，不做外部搜索、数据采集或第三方拉取。所有输入必须来自系统已经入库的数据。

当前核心边界：

- 每个 `analyst_view` run 完全独立，不读取、不参考、不继承历史 run。
- 每个分析师 Profile 独立运行一次，单个失败不影响其他 Profile。
- 允许读取快照中已经入库的价格、市值、估值倍数、目标价、持仓成本等字段或文本。
- 允许按分析师框架讨论安全边际、估值纪律、价格与市值相关事实。
- 不因为 `price_sensitive=true` 自动剔除外部 Evidence，也不对财务、公告、外部证据做价格脱敏。
- 不声称读取快照以外的信息，不生成搜索 query，不要求联网搜索。
- 模型输出必须是结构化 JSON，并通过 Profile、规则覆盖和引用有效性校验。

## Fact Ledger

008 在调用模型前会构建 `fact_ledger`，用于把当前快照的事实基础和可解释评分集中记录下来。

主要字段：

- `analysis_basis`：本次使用的财务期间、公告 id、外部证据 id、会计事件数量和说明。
- `profile_relevance`：分析师框架与公司类型的适配度，由服务层规则计算。
- `data_confidence`：本次快照的数据质量和完整度，由服务层规则计算。
- `financial_quality`：财务期数、报表类型、可比性和现金流信息概览。
- `external_evidence_quality`：外部证据数量、结构化状态、待复核数量和可信度概览。
- `accounting_events`：会计政策、会计估计、差错更正、追溯调整、收入确认、核算方式变化、非经常性因素等事件。

写入 run 前，服务层会用 `fact_ledger` 覆盖模型输出中的：

- `profile_fit_score`
- `confidence`
 - `analysis_basis`
 - `accounting_events`
 - `score_explanations`
  - 外部证据的模型输入字段已收敛为 5 个字段，避免把 `importance_score`、`credibility_score`、`use_scope`、`analysis_note` 等 007 评分和复核字段直接带入分析师视角。

含义：

- `profile_fit_score` 是分析师框架与公司类型的适配度，不是看多/看空强度。
- `confidence` 是当前快照数据质量，不是观点正确概率。

## 运行流程

单个分析师运行入口：

- `run_company_analyst_view(...)`

流程：

1. 校验 Profile 是否存在。
2. 构建当前公司、当前 Profile 的输入快照。
3. 计算 `data_snapshot_hash`。
4. 创建 `AnalysisRun(status="running")`。
5. 调用 `ModelGateway.generate_structured(...)`。
6. 用 `fact_ledger` 覆盖评分和依据字段。
7. 校验输出 Profile、规则覆盖和引用有效性。
8. 成功时覆盖同公司同 Profile 的当前 `analyst_view` 记录，写入 `status="success"`、`result`、`confidence`、`is_latest=true`。
9. 失败时同样覆盖同公司同 Profile 的当前 `analyst_view` 记录，写入 `status="failed"`、`result.error`、`result.error_type`、`is_latest=true`；错误文本会做清洗和压缩。

当前 `parent_run_id` 固定为空，避免 run 之间形成继承关系。

批量运行入口：

- `run_company_analyst_views_batch(...)`

行为：

- 请求为空数组时默认运行全部 Profile。
- 可以指定部分 Profile。
- 每个 Profile 独立生成。
- 单个 Profile 失败不会阻断其他 Profile。
- 每个 Profile 最多保留一条最新 `AnalysisRun`；新分析会覆盖同公司同 Profile 的旧记录。

## 引用校验

写入 success 前会校验：

- `analyst_profile` 必须等于请求 Profile。
- `rule_checks` 必须覆盖当前 Profile 的全部规则。
- `supporting_evidence_ids` 必须来自当前快照中的 `external_evidence/evidence id`。
- `rule_checks[].evidence_ids` 必须来自当前快照中的 `external_evidence/evidence id`。
- `rule_checks[].announcement_ids` 必须来自当前快照中的公告 id。
- `rule_checks[].financial_periods` 必须来自当前快照中的财务期间。

引用无效时：

- 当前 run 写入 `status="failed"`。
- `result.error_type="ModelOutputValidationError"`。

## Run 记录策略

008 使用通用 `analysis_runs` 表。

固定标识：

- `run_type="analyst_view"`
- `run_version="008_v1"`
- `prompt_version="analyst_view_v1"`

记录策略：

- 每个公司、每个分析师 Profile 只保留一条最新 `analyst_view` run。
- 新分析启动时复用同公司同 Profile 的最新记录，并删除该 Profile 其他旧 `analyst_view` 记录。
- 新分析成功时覆盖为 `status="success"`、`is_latest=true`。
- 新分析失败时覆盖为 `status="failed"`、`is_latest=true`，用于前端展示最新失败原因。
- 删除只能由用户通过删除接口显式触发；删除后该 Profile 暂无分析记录。
- 历史 run 不再作为 008 的持久保留目标，也不进入下一次 008 输入。

公司工作台的分析师视角区域会展示：

- 全部分析师 Profile。
- 每个 Profile 的中文名、英文名、简介和规则 chips。
- 最新成功 run。
- 最近失败 run。
- 数据置信度。
- 视角适配度。
- 关键观察。
- 本次分析依据。
- 评分解释。
- 会计口径提示。
- 规则检查结果。
- 财务观察。
- 公告观察。
- 风险、缺口、反方证据、估值假设建议。
- 后续问题。

操作：

- 单个 Profile 生成。
- 批量生成全部或多个 Profile。
- 生成中可停止前端等待请求。
- 可显式删除指定 run 记录。

时间显示：

- 分析师 run 的生成时间统一按东八区 `Asia/Shanghai` 显示。
- 后端如果返回 SQLite 常见的无时区时间字符串，例如 `2026-08-09 00:40:00.000000`，前端按 UTC 解析后再转换为东八区显示。
- 带 `Z` 或显式时区偏移的 ISO 时间按其原始时区语义解析，再转换为东八区显示。

注意：

- 停止按钮取消的是当前前端 HTTP 等待；如果后端已经完成处理，仍可能写入已经开始的 run。
- 删除 run 是真实删除数据库记录，只在用户显式点击时发生。

## 2026-08-14 前置证据梳理与优化草案

当前 008 分析师视角读取的前置证据口径：
